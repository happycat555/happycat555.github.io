打开界面时，底栏没有贴住屏幕边缘。检查 Widget，四边对齐已经勾选，边距也没有问题，但运行效果仍然不对。

这类问题很容易让人怀疑适配参数、分辨率或者资源缓存。这次排查最终指向了一个更具体的原因：**入场动画先改变了节点的缩放，Widget 随后使用这个缩放值计算布局，而动画结束后没有再次触发布局计算。**

本文按“发现问题、提出解法、解决问题”还原排查过程。生命周期结论以 **Cocos Creator 2.4.12 的运行时实现**为依据；节点名称、尺寸和代码均使用通用示例，不对应具体业务。

## 一、发现问题：Widget 配置正确，为什么布局还是不对？ {#diagnosis}

### 1. 先确认配置，再追踪运行时行为

界面结构可以简化为：

```text
ScreenRoot
└─ ContentRoot
   ├─ Background
   ├─ Content
   └─ BottomBar
```

根节点负责适配屏幕，内容容器承载主体内容和底栏。底栏的 Widget 默认相对内容容器进行对齐。

最初检查保存后的 prefab 时，发现内容容器没有 Widget。根节点虽然会被框架拉伸到全屏，但内容容器仍然保留设计尺寸，子节点自然也只能相对这个固定尺寸对齐。

给内容容器补上四边拉伸，是必要的一步。但配置保存后，打开界面时仍然出现偏移。这说明“缺少 Widget”只解释了第一层问题，还需要继续检查运行时谁在修改节点。

接下来发现：**内容容器还参与了一段入场缩放动画。**

例如，动画让它在一秒内从 `scale = 1.2` 缩放到 `scale = 1`。与此同时，它的 Widget 使用的是 `ON_WINDOW_RESIZE` 模式。

这两个配置单独看都合理，组合起来却存在时序冲突。

### 2. Widget 拉伸时，会考虑节点当前的缩放

Widget 要让节点缩放后的边界满足对齐约束。因此，在四边拉伸、边距为零、目标为直接父节点的简化场景下，可以把计算理解为：

```text
节点宽度 = 父容器可用宽度 / 节点 scaleX
节点高度 = 父容器可用高度 / 节点 scaleY
```

假设父容器尺寸是 `720 × 1280`，Widget 执行时内容容器的缩放已经变成 `1.2`：

```text
width  = 720 / 1.2  = 600
height = 1280 / 1.2 ≈ 1066.67
```

此时乘上 `1.2` 的缩放，容器边界仍然满足全屏约束，所以这次计算本身没有错。

问题出现在动画结束后：

```text
scale 恢复为 1
width、height 仍然是 600 × 1066.67
```

如果没有新的对齐操作，内容容器就保留了偏小的尺寸。底栏依然相对这个容器贴底，因此它的位置也会偏离屏幕底边。

### 3. 真正决定结果的是一帧中的执行顺序

继续查看引擎源码，可以发现 Widget 的注册和实际对齐分处两个时机。

- `Widget.onEnable()`：把组件加入待对齐队列。
- `WidgetManager`：监听 `Director.EVENT_AFTER_UPDATE`，统一执行对齐。

相关顺序如下：

```text
onLoad
  ↓
onEnable：Widget 加入待对齐队列
  ↓
start：Animation 的 Play on Load 启动默认动画
  ↓
组件 update
  ↓
调度器更新，包括 Animation 动画更新
  ↓
组件 lateUpdate
  ↓
EVENT_AFTER_UPDATE：Widget 执行对齐
  ↓
后续渲染流程
```

这里有两个容易混淆的细节。

**第一，Play on Load 实际在 Animation 的 `start()` 中处理。** 名称里虽然有 Load，但它并不在 `onLoad()` 回调里直接启动默认动画。启用了自动播放、存在默认动画且当前没有正在播放的动画时，才会执行自动启动。

**第二，Widget 在 `onEnable()` 中注册，不代表它会立即完成布局。** 等到帧末真正计算时，动画已经有机会把缩放改为 `1.2`。

如果项目使用框架手动播放入场动画，启动位置可能不同，也需要检查实际调用链。关键是确认：动画是否在首次自动对齐之前修改了缩放。

### 4. ON_WINDOW_RESIZE 不是“节点一变化就重新对齐”

在这个版本中，三种模式的主要区别是：

| 模式 | 自动对齐时机 |
| --- | --- |
| `ONCE` | 每次组件启用后，对齐一次 |
| `ON_WINDOW_RESIZE` | 每次组件启用后对齐一次，窗口适配变化时再次对齐 |
| `ALWAYS` | 启用期间每帧对齐 |

运行时，`ON_WINDOW_RESIZE` 会响应 `cc.view` 的 `canvas-resize` 和窗口的 `orientationchange` 等事件，把相关 Widget 重新加入队列。实际对齐仍然发生在随后的管理器更新阶段。

**普通节点的缩放或尺寸变化，不等同于窗口 resize。** 因此动画把缩放从 `1.2` 改回 `1`，不会自动触发这个模式重新对齐。

另外，完成一次对齐后退出管理器的更新队列，也不意味着组件的 `enabled` 被设为了 `false`。所以检查器里看到 Widget 仍然启用，不能据此判断它还在逐帧更新。

排查中使用该版本引擎的对齐代码进行了模拟：动画结束后，容器确实保留了首次计算得到的小尺寸；触发窗口变化后，尺寸才恢复正常。这与界面“看起来没有适配”的现象吻合。

## 二、提出解法：让布局和动画各自在合适的时机工作 {#solutions}

找到原因后，约束也很明确：希望保留现有节点树和入场缩放效果。

可以考虑几种方案：

| 方案 | 效果与代价 |
| --- | --- |
| 把布局容器与动画节点分层 | 职责清晰，但需要调整节点树 |
| 将相关 Widget 改为 `ALWAYS` | 持续重新计算布局，可能改变原来的缩放观感 |
| 动画结束后统一刷新布局 | 改动较少，但动画结束时可能出现位置跳变 |
| 动画前完成布局，播放期间禁用相关 Widget | 保留已有结构，让动画使用已经确定的布局尺寸 |

最后选择了第四种思路。

### 1. 为什么只在 onLoad 中提前对齐还不够？

一个直观想法是：既然动画晚于 `onLoad()`，那就在 `onLoad()` 里提前调用 `updateAlignment()`。

但 `updateAlignment()` 只会立即计算一次，**不会取消后续的自动对齐**。如果只做这一件事，仍然可能出现：

```text
onLoad：手动对齐，scale = 1，尺寸正确
  ↓
Widget 进入自动对齐队列
  ↓
动画更新：scale = 1.2
  ↓
帧末自动对齐：尺寸再次被除以 1.2
```

所以需要补上关键步骤：**对齐完成后，暂时禁用参与缩放的容器 Widget。**

禁用不会清空它已经计算好的位置和尺寸。动画仍然可以正常改变缩放，最终回到 `scale = 1` 时，容器也自然回到正确的布局大小。

### 2. 动画结束后，是否必须恢复 Widget？

这取决于后续需求。

如果界面只在打开时确定一次布局，之后没有窗口、方向和父容器尺寸变化，可以保持这个 Widget 禁用，不必专门恢复。

如果仍需支持窗口适配，就在动画缩放回到 `1` 后恢复。重新启用组件会触发 `onEnable()`，让它再次进入对齐队列。若需要在当前调用中立即读取最新坐标，可以手动刷新。

这里还要区分容器和子节点：`updateAlignment()` 会处理自身及所需的祖先 Widget，但不会自动遍历后代。如果父容器尺寸发生变化，需要结合子节点的更新模式，决定是否按父到子的顺序补一次刷新。

## 三、解决问题：最小实现，以及验证中需要分清的边界 {#implementation}

### 1. 用伪代码表达核心流程

下面的示例通过预先绑定的组件引用定位布局容器。`layoutWidgets` 按父到子排列；真正需要暂停的，是参与入场缩放的容器 Widget，不必把整棵节点树上的组件全部禁用。

```text
onLoad():
    # 前提：入场动画尚未修改缩放，容器的初始 scale 为 1
    updateRootLayout()

    for widget in layoutWidgets:
        if widget.enabled:
            widget.updateAlignment()

    pausedWidgets = []

    for widget in animatedContainerWidgets:
        if widget.enabled:
            widget.enabled = false
            pausedWidgets.append(widget)

    # 根据需求，订阅实际入场动画的完成事件或使用框架提供的完成回调
    entrancePlayer.onFinishedOnce(restoreWidgets)


restoreWidgets():
    # 前提：入场缩放已经恢复为 1
    for widget in pausedWidgets:
        widget.enabled = true

    pausedWidgets.clear()
```

如果界面不再需要动态适配，完成事件的订阅和恢复函数都可以省略。

如果需要处理动画中断，应当在中断路径中明确决定：是否把缩放重置为 `1`，以及是否恢复 Widget。不能在缩放仍为中间值时直接恢复，否则会重新引入同样的问题。

### 2. 为什么反复开关正常，而 onLoad 又只执行一次？

实现过程中，一个容易过度推导的问题是：`onLoad()` 只执行一次，那么布局初始化是不是一定要放到每次打开都会执行的业务回调中？

答案取决于界面实例是否被复用。

这次沿关闭链路继续检查后，确认正常返回会销毁界面节点；再次打开时，会重新实例化 prefab。因此，每次打开对应一个新实例，也就会重新执行 `onLoad()`。

```text
关闭 → 销毁旧实例
再次打开 → 创建新实例 → 再次执行 onLoad
```

使用者反复开关界面，布局始终正常，与这个调用链完全一致。

只有在“关闭时缓存实例、再次打开时复用”的路径下，才需要考虑把初始化放到每次打开的回调中。**不能仅凭 `onLoad()` 只执行一次，就认定当前界面的重复打开存在问题；应先确认关闭究竟是销毁还是隐藏。**

### 3. 布局正常，不代表动画完成回调一定执行了

代码审查还发现了一个独立于布局表现的隐患：同一个节点上可能同时存在普通 Animation 和框架提供的入场动画组件。

如果普通 Animation 已被禁用，而实际播放的是另一个组件，那么按基类获取第一个 Animation，就可能把完成监听注册到没有播放的组件上。

此时仍然可能看到正确的界面：

```text
提前对齐成功
  ↓
Widget 被禁用，布局尺寸保持正确
  ↓
动画正常播放
  ↓
恢复回调没有触发，但静态布局依然正常
```

因此，需要分别验证两个结论：

- **布局修复是否生效**：动画前后尺寸和位置是否正确。
- **恢复逻辑是否生效**：动画结束后 Widget 是否真的恢复启用。

恢复逻辑应监听实际播放的组件。框架已经提供入场动画完成回调时，可以直接使用该回调，减少重复监听和组件选择错误。

本文的伪代码表达的是这一约束；视觉测试正常本身，不能证明所有完成回调都已经执行。

### 4. 一个实现细节：遍历子节点要用 for...of

编写布局遍历时，还遇到了一个 TypeScript 问题：为什么循环里的“子节点”会被推断成 `string`？

原因是使用了 `for...in`。

```ts
// 得到的是属性键，例如 "0"、"1"
for (const key in children) {
    // key 是 string
}

// 得到的才是数组中的节点对象
for (const child of children) {
    // child 是节点
}
```

同时要注意遍历范围：`children` 只包含直接子节点。如果当前根节点下只有一个需要处理的内容容器，这个范围就足够；只有需要处理更多层级时，才增加递归或后代组件遍历。

### 5. 验证结果和后续适用范围

本次排查中，引擎代码模拟支持了“缩放参与首次对齐、动画结束后尺寸残留”的原因判断；提前对齐并暂停容器 Widget 的实现，也通过了使用者的实际反复开关验证。

若还需要支持窗口变化、缓存复用或动画中断，则应针对对应路径继续验证，不能把普通开关测试的结果推广到所有场景。

后续排查同类问题时，可以沿着这条顺序收集证据：

1. 确认保存后的 prefab 配置，以及运行时实际加载的组件。
2. 找出会改变节点位置、尺寸和缩放的脚本或动画。
3. 比较这些修改与 Widget 实际对齐的先后顺序。
4. 区分首次布局正确、动画结束后恢复正确、后续适配正确这几个独立结果。
5. 根据真实的销毁或缓存路径，选择初始化所在的生命周期。

这次问题的关键，在于让布局计算发生在缩放基准明确的时刻，并在动画期间保留这个结果。把这个时序理顺之后，不调整节点树，也能让现有布局和入场动画协调工作。
