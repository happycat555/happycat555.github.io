懒加载的思路很直观：把某项工作推迟到真正需要它的时候再做。图片进入可视区域再下载，用户打开报表页再加载图表库，第一次查询时再创建搜索索引，都属于这种思路的应用。

它可以减少启动开销，也可能把延迟、错误和初始化顺序问题转移到用户首次使用的时刻。理解懒加载，需要同时回答两个问题：**延后了什么工作，以及谁来保证这项工作在需要时已经完成？**

## 1. 先区分三个容易混淆的概念 {#section-1}

| 概念 | 关注的问题 | 通用示例 |
| --- | --- | --- |
| 懒加载 | 资源或代码什么时候加载 | 打开编辑器时才下载编辑器模块 |
| 懒实例化 | 对象什么时候创建 | 第一次导出文档时才创建导出器 |
| 单例 | 在约定范围内共享多少个实例 | 多个页面使用同一个设置服务 |

三者可以组合，也可以独立存在。

单例可以在启动时立即创建，也可以第一次访问时才创建。按需创建的对象也不一定是单例，例如每次打开预览窗口，都可以创建一个新的预览器。

还要注意，**延迟创建对象，不代表延迟加载它所在的代码文件**。代码可能已经被下载、解析和执行，只是尚未调用构造函数。判断性能收益时，要看实际延后的工作，不能只看代码中有没有一个延迟获取实例的入口。

本文使用“懒加载”讨论一般策略；涉及对象构造时，明确称为“懒实例化”。

## 2. 它能带来哪些收益？ {#section-2}

### 减少启动阶段的工作

假设一个应用提供首页、搜索和报表功能。报表模块需要加载图表库、读取模板并建立计算缓存，但许多用户只浏览首页。

如果启动时就完成全部工作，每个用户都会承担报表功能的成本。按需加载后，首页可以更早可用，没有打开报表的用户也不必支付这部分成本。

收益的大小取决于延后的工作是否昂贵、是否位于启动关键路径，以及实际有多少用户会使用它。一个只包含几个数字字段和空数组的对象，通常没有必要仅为启动性能设计复杂的延迟创建机制。

### 避免为未使用的功能分配资源

大型缓存、解码器和预览器可能占用较多内存。延后创建可以降低启动时的内存占用，有些对象在整个会话中都不会被创建。

但懒加载本身不负责释放资源。如果对象使用后一直保留，长期运行后的内存占用仍可能接近提前创建的方案。**按需创建和按需释放是两项独立设计。**

### 更容易支持低频或条件功能

部分能力只在特定用户、设备或操作下需要。让这些能力按需准备，可以减少无关用户承担的成本，也能避免它们拖慢普通流程。

不过，单纯延迟实例化不会自动解决模块拆包、平台兼容或依赖导入的问题。若目标是避免加载某段代码，还需要相应的模块加载机制支持。

## 3. 它把哪些成本推迟到了后面？ {#section-3}

### 首次使用的延迟

用户第一次点击“生成报表”时，可能需要等待模块下载、对象创建和数据准备。启动变快了，首次操作却可能变慢。

如果这项功能几乎每个人都会立即使用，延迟加载可能只是把等待挪到了更显眼的位置。可以根据使用概率选择提前准备：例如进入相关页面后预取资源，或在空闲时构建缓存。

预加载也有代价，会占用网络、CPU 和内存，应通过测量选择时机。

### 错误出现得更晚

提前初始化可以较早暴露缺少资源、配置错误或构造失败。懒加载则可能把这些问题推迟到一个低频操作，甚至在线上运行很久后才出现。

因此，延迟加载的功能需要明确的失败反馈、重试策略和独立验证。主流程启动成功，并不能证明所有延迟功能都能正常使用。

### 创建时机和调用链更难追踪

当多个模块都能访问一个懒单例时，首次创建可能由页面打开触发，也可能由一次权限查询、日志记录或后台检查触发。

如果构造函数只设置默认字段，影响通常很小。如果它还启动任务、注册监听或访问网络，一次看似普通的查询就可能触发一串副作用。

### 并发请求和异步初始化需要额外处理

两个调用方可能同时请求尚未准备好的资源。如果没有共享正在进行的加载任务，就可能重复下载、重复创建连接或重复构建缓存。

即使在单线程事件循环中，异步操作也会交错执行，不能把“单线程”等同于“不会重复初始化”。多线程环境还需要考虑同步与内存可见性。

对于异步资源，常见做法是让调用方共享同一个准备任务，并明确失败后是保留失败结果，还是允许重新尝试。

## 4. 懒实例化会增加耦合吗？ {#section-4}

可能会，但必须分清耦合来自哪里。

| 现象 | 主要来源 |
| --- | --- |
| 一个模块直接引用另一个模块的具体类 | 实现依赖 |
| 到处读取同一个全局对象 | 全局访问与共享状态 |
| 功能必须等某个对象被首次访问后才能工作 | 懒实例化引入的时序依赖 |
| 两个对象在构造期间互相获取对方 | 构造依赖与延迟创建相互作用 |

### 直接依赖不会因为提前创建而消失

例如，通知模块直接调用会员模块，判断某个用户是否具备资格。无论会员对象在启动时创建，还是首次访问时创建，通知模块都依赖会员模块的实现。

把创建时机提前，不会改变这条依赖关系。要减少实现耦合，需要调整接口、职责或依赖方向。

### 更隐蔽的是时序耦合

假设会员模块在构造函数中向通知服务注册一个处理器。只有首次访问会员对象，注册才会发生。

程序可能表现为：

```text
先打开会员页面
  → 创建会员对象
  → 完成处理器注册
  → 后续通知能够处理

先收到会员通知
  → 会员对象尚未被访问
  → 处理器尚未注册
  → 通知无法按预期处理
```

表面上两个模块可能通过接口协作，但实际要求用户先访问某个页面。这就是时序耦合：**正确性依赖一个没有被明确表达的执行顺序。**

把直接调用改为事件，也不能自动解决这个问题。如果订阅仍发生在懒对象的构造函数中，订阅建立前的事件仍可能被错过，除非事件机制明确支持缓存与重放。

### 构造期间相互访问可能递归创建

一种常见实现会先完成构造，再把新对象保存到单例缓存。如果两个对象构造时互相访问，就可能形成下面的调用链：

```text
获取 A
  → A 尚未创建，开始构造
    → 构造过程中获取 B
      → B 尚未创建，开始构造
        → 构造过程中再次获取 A
          → A 尚未写入缓存，再次开始构造
```

结果可能是递归直到栈溢出。某些实现会检测“正在创建”并报错，但这只是让问题更容易定位，并没有消除循环依赖。

把未完成构造的对象提前暴露出去也有风险：调用方可能读到不完整状态。通常更应该拆分构造和跨模块协作，调整依赖关系。

## 5. 对象存在，不等于业务数据就绪 {#section-5}

这是使用懒单例时容易忽略的一点。

例如，一个账户对象可以在第一次查询时立即创建，但账户资料仍需要登录后从服务器获取。取得对象，只说明它已经存在，不代表资料已经加载完成。

至少需要区分三件事：

1. **对象创建**：准备字段、容器和基本结构。
2. **运行机制启动**：建立必须存在的注册关系，启动监听或调度。
3. **业务数据就绪**：加载当前用户、环境或会话所需的数据。

这三件事可以发生在不同时间。把它们全部塞进构造函数，往往会同时引入顺序、失败恢复和账号切换问题。

如果某个操作必须等待数据，应通过明确的就绪状态或可等待的准备接口表达，而不是让调用者根据默认值猜测。

## 6. 保留懒实例化，怎样控制它的副作用？ {#section-6}

### 让构造函数保持简单

构造函数适合设置默认值、建立轻量容器和保存显式传入的依赖。全局注册、启动轮询、网络请求，以及复杂的跨模块调用，更适合放到有明确调用时机的方法中。

判断标准是：一个调用方第一次获取对象时，是否会意外改变系统其他部分的行为？如果会，就应当重新审视这段初始化职责。

### 为必须执行的工作提供明确入口

必须从应用运行早期就生效的处理器，可以由启动流程集中注册。注册时保存函数，执行函数时再访问相应对象，这样仍然可以保留对象的按需创建。

```text
应用启动
  → 注册各功能处理器

实际请求到来
  → 选择对应处理器
  → 按需获取业务对象
  → 执行处理
```

注册成功并不意味着业务数据已经准备好，处理器仍需遵守登录状态和数据就绪条件。

这种设计把“必须建立的协作关系”和“可以延后的对象创建”分开，不需要让所有对象都提前实例化。

### 明确资源的生命周期

除“何时创建”之外，还应确定谁拥有对象、何时停止后台任务、何时清理缓存，以及用户或会话变化后哪些状态需要重置。

全局单例缺少重置接口，会影响测试隔离和会话切换。这是单例生命周期的问题，不能归因于懒加载，也不能仅靠提前创建解决。

### 测量首次体验和长期成本

验证懒加载方案时，可以同时观察：

- 启动到首个可交互界面的耗时。
- 功能首次使用与后续使用的耗时。
- 启动后和长时间运行后的内存占用。
- 同时触发时是否重复初始化。
- 加载失败后能否恢复。
- 不同功能访问顺序下，行为是否一致。

只比较启动时间，容易把转移到首次操作上的成本漏掉。

## 7. 如何选择合适的策略？ {#section-7}

| 场景 | 更适合的做法 |
| --- | --- |
| 创建成本高、使用概率低的功能 | 优先考虑懒加载或懒实例化 |
| 几乎所有用户都会立即使用的功能 | 考虑提前准备，或有依据地预加载 |
| 必须随时接收通知的全局处理机制 | 使用明确的启动注册入口 |
| 字段少、没有副作用的状态对象 | 可以按需创建，但不必高估性能收益 |
| 需要加载业务数据的对象 | 将对象创建与数据准备分开 |
| 多调用方共享的异步资源 | 共享准备任务，明确失败和重试行为 |
| 与用户或会话绑定的缓存 | 同时设计创建、失效和重置规则 |

懒加载优化的是工作的发生时机。设计时既要考虑省下了多少不必要的工作，也要明确谁承担首次等待、谁保证初始化顺序，以及失败后如何恢复。保留按需创建，同时为必要的注册和数据准备建立明确入口，往往能兼顾启动效率与行为的可预测性。
